# Instructions - Étape 9 : Distributions "pour tous" (`*`) & Codes spéciaux (`codes.json`)

## Objectif
1. Le Google Sheet de l'Étape 8 accepte `*` dans la colonne `uuid` : la ligne est alors destinée à **tous** les comptes.
2. Refonte du système Redeem (Étape 7) : les codes sont désormais décrits dans `settings/codes.json` (format riche : plusieurs récompenses, fenêtre de disponibilité, répétable ou non).
3. Les codes réclamés apparaissent dans l'**historique des cadeaux**, catégorie `codes`.

Les codes personnels générés à partir d'un UUID (`useritem`) et le lien `?Redeem=` sont traités à l'**Étape 10**. Le pipeline écrit ici doit être conçu pour les accueillir (voir "Extensibilité").

## Spécifications

### 1. Distributions `*` (GiftManager)
- Une ligne dont `uuid` vaut `*` (après `trim`) est traitée comme destinée à l'utilisateur courant, **sans comparer l'UUID**. Le reste est identique à l'Étape 8 : `n > lastCheckedLine`, validation `type`/`quantity`/`key`, anti-doublon via `gifts_received[n]`, une seule transaction.
- Dans `gifts_received`, l'enregistrement stocke l'UUID **réel** du compte et ajoute `broadcast: true`.
- Conséquence assumée (à documenter en commentaire dans `GiftManager.js`) : un compte créé après coup reçoit **toutes** les lignes `*` historiques du sheet, puisque `lastCheckedLine` démarre à 1. Ne mettre dans `*` que des cadeaux qu'on accepte de voir rétroactivement distribués.

### 2. `settings/codes.json`
Tableau d'objets. Le champ `_comment` est ignoré par le code.
```json
[
  {
    "_comment": "Usage unique : 1 booster A1 + carte SERIE-A1 / P004 (fullart si dispo, sinon la première avec cet index).",
    "Code": "WELC0M3ST3V3",
    "Rewards": [
      { "RewardType": "Booster", "Quantity": 1, "ItemId": "A1" },
      { "RewardType": "Card", "Quantity": 1, "ItemId": "SERIE-A1 / P004", "PreferedLayout": "fullart" }
    ],
    "Availabilities": null,
    "Repeatable": false
  },
  {
    "_comment": "Répétable à l'infini, disponible avant le 15 octobre 2026.",
    "Code": "IM.A.CHEAT3R.",
    "Rewards": [
      { "RewardType": "Booster", "Quantity": 3, "ItemId": "A1" },
      { "RewardType": "Card", "Quantity": 1, "ItemId": "SERIE-A1 / Z001", "PreferedLayout": null }
    ],
    "Availabilities": { "StartDate": null, "EndDate": "2026-10-15" },
    "Repeatable": true
  }
]
```
Sémantique :
- **`Code`** : comparaison insensible à la casse, `trim` des espaces. Les points et autres caractères sont conservés.
- **`RewardType: "Booster"`** : `ItemId` = id du set (clé de `settings/boosters/<ItemId>.json`). Appelle `DateSyncManager.addBonusBoosters(ItemId, Quantity)`.
- **`RewardType: "Card"`** : `ItemId` = `Index` de la carte dans les JSON de boosters (ex. `"SERIE-A1 / P004"`). Résolution de la carte :
  1. si `PreferedLayout` est non nul : première carte avec cet `Index` **et** ce `Layout` ;
  2. sinon (ou si aucune ne correspond) : première carte avec cet `Index`, dans l'ordre du JSON ;
  3. aucune carte avec cet `Index` : récompense invalide.
  Appelle `BoosterManager.addCardToCollection(card, Quantity)`.
- **`Quantity`** : entier > 0.
- **`Availabilities`** : `null` = toujours disponible. Sinon `StartDate` et `EndDate` (`YYYY-MM-DD`, jours UTC, chacun nullable). Règle : `StartDate` **inclus**, `EndDate` **exclu** ("avant le 15 octobre" = valable jusqu'au 14 inclus). Le jour UTC vient de `DateSyncManager` (jamais `Date.now()`).
- **`Repeatable: false`** : le code est inscrit dans `redeemed_codes` (`{ code: <CODE EN MAJUSCULES>, redeemedAt }`) et refusé s'il y est déjà. **`Repeatable: true`** : jamais inscrit dans `redeemed_codes`, réclamable sans limite.

### 3. `RedeemManager.js`
API (stable, réutilisée à l'Étape 10) :
- `async inspect(rawCode)` → **sans aucune écriture**. Retourne `{ status, kind, rewards? }` avec
  `status ∈ "ok" | "unknown" | "expired" | "not_yet_available" | "already_used" | "invalid_config"`
  et `rewards` = liste déjà résolue `[{ type: "booster"|"card", key, quantity, card? }]` (pour l'aperçu).
- `async claim(rawCode)` → refait `inspect` **à l'intérieur de la transaction d'écriture** (anti double-clic et anti course), puis, dans **une seule transaction** (`StorageRepository.transaction`) : toutes les récompenses + `redeemed_codes` (si non répétable) + enregistrements d'historique (§4). Les fonctions `addBonusBoosters` / `addCardToCollection` doivent accepter un contexte de transaction optionnel (même mécanisme qu'à l'Étape 8).
- Atomicité : si **une** récompense est invalide (set ou carte introuvable, quantité incorrecte), le code entier est refusé avec `invalid_config`, rien n'est consommé, `console.warn` sans afficher le code.
- Le fichier `codes.json` est chargé **à la demande** (au premier `inspect`), jamais au démarrage, jamais listé ni exposé dans l'UI, jamais loggé.

> Limite à documenter en commentaire : `codes.json` est servi au navigateur, donc lisible par quiconque ouvre les outils de développement. "Ne pas montrer" les codes est une règle d'interface, pas une protection. *(Option de durcissement, facultative : accepter `CodeHash` (SHA-256 hex du code normalisé en majuscules) à la place de `Code`.)*

### 4. Historique : catégorie `codes`
- Chaque récompense appliquée crée un enregistrement dans `gifts_received` (même store, **pas de changement de version de la base**) :
  `{ line: "code:<redeemId>:<i>", category: "codes", uuid, type: "booster"|"card", key, quantity, receivedAt }`
  où `redeemId = crypto.randomUUID()` (identique pour toutes les récompenses d'un même claim) et `i` = index de la récompense. `key` = id du set ou clé unique `id_style` de la carte. **Le code lui-même n'est jamais stocké dans l'historique.**
- Les enregistrements issus du sheet reçoivent `category: "distribution"`. Un enregistrement **sans** `category` (anciennes sauvegardes) est traité comme `distribution`.
- `gifts_received` contient donc des clés **numériques** (lignes du sheet) et **chaînes** (codes). Vérifier que `GiftManager` (anti-doublon) et `SaveFile.importFromFile` (validation Étape 6) acceptent les deux types de clés.
- **`GiftsView`** : tri par `receivedAt` décroissant (et non plus par n° de ligne). Badge de catégorie ("Distribution" / "Codes"), filtre Tous / Distributions / Codes. Le n° de ligne n'est affiché que pour `distribution`. Pour `codes`, afficher le libellé de la récompense (set ou carte + aperçu) sans le code.

### 5. `RedeemView.js`
- Champ de saisie + bouton "Valider". Flux : `inspect` → si `ok`, modal de confirmation listant les récompenses (noms résolus, aperçu des cartes) avec "Récupérer" / "Annuler" → `claim` → modal/toast de succès.
- Statuts non `ok` : toast d'erreur traduit (`redeem.error.unknown`, `.expired`, `.not_yet_available`, `.already_used`, `.invalid_config`). Aucun effet sur le quota.
- Bouton "Récupérer" désactivé dès le premier clic. Header mis à jour via `QUOTA_UPDATED`.
- Ajouter toutes les clés FR/EN dans `settings/i18n/*.json`.

### 6. Extensibilité (pour l'Étape 10)
`inspect`/`claim` ne doivent pas supposer que le code vient de `codes.json` : isoler la résolution dans une méthode interne `resolveCode(rawCode)` qui retourne `{ kind: "special" | "useritem", rewards, repeatable, storeKey }`. L'Étape 10 y ajoutera le type `useritem` sans toucher au reste.
