# Instructions - Étape 10 : Codes personnels `useritem` & lien `index.html?Redeem={code}`

## Objectif
1. Codes **générés à la demande** pour **un seul utilisateur** (UUID), **un item**, **une quantité**, **à usage unique**, vérifiables **hors-ligne** par l'app.
2. Charger `index.html?Redeem={code}` ouvre directement la popup de réclamation, sauf si le code est déjà utilisé ou n'est pas destiné à ce compte.

L'algorithme complet, les formats binaires et les vecteurs de test sont dans **`.docs/gamemaster/useritemcode.md`** (fichier fourni avec cette étape : le placer tel quel). Le code doit s'y conformer ; en cas d'écart, **corriger le code, pas le document**.

## Fichiers
- `.docs/gamemaster/useritemcode.md` (fourni)
- `js/business/UserItemCode.js` (nouveau)
- `js/business/RedeemManager.js` (ajout du type `useritem`), `js/UI/views/RedeemView.js`
- `js/utils/DeepLink.js` (nouveau), `js/app.js`, `js/UI/views/OnboardingView.js`, `index.html`
- `settings/config.json` (`useritemCode`), `settings/i18n/*.json`

## Spécifications

### 1. `settings/config.json`
Ajouter `"useritemCode": { "version": 1, "key": "<base64 de 32 octets>" }`. Livrer une clé **placeholder** ; le game master la remplace (`openssl rand -base64 32`) et utilise la même dans son générateur. Rappel à mettre en commentaire (ou dans le README) : cette clé est servie au navigateur, donc extractible (voir "Modèle de sécurité" du document).

### 2. `UserItemCode.js` (vérification côté app uniquement)
- `normalize(raw)` : majuscules, suppression de `-` et des espaces, `O→0`, `I→1`, `L→1`.
- `async verify(raw, uuid, catalog)` → `{ status, rewards? , storeKey? }`, `status ∈ "ok" | "invalid_format" | "wrong_user" | "invalid" | "unknown_item"`, dans l'ordre décrit par le document. Comparaison du MAC en **temps constant**. Implémentation via `crypto.subtle` (`HMAC`/`SHA-256`), contexte sécurisé requis (HTTPS ou localhost) : le mentionner dans le README.
- Résolution de l'item : construire, à la demande, la table `hash24(canonicalItem) → item` sur tous les sets (`booster:<setId>`) et toutes les cartes (`card:<Index>|<Layout>`). Zéro ou plusieurs correspondances : `unknown_item` (le code n'est pas consommé).
- `async selfTest()` : rejoue les vecteurs de test du document (clé de test passée en paramètre, **jamais** la vraie clé). Appelable depuis la console en dev.

### 3. `RedeemManager.js`
- `resolveCode(rawCode)` (Étape 9) : essayer d'abord `codes.json` (code spécial), puis, si la forme normalisée fait 32 caractères Crockford, `UserItemCode.verify`.
- Statuts supplémentaires exposés par `inspect` : `"invalid_format" | "wrong_user" | "invalid"` (les trois s'affichent comme erreurs distinctes dans l'UI ; `invalid` et `unknown` partagent le même texte utilisateur pour ne pas révéler plus que nécessaire).
- Usage unique : `redeemed_codes` avec `code` = forme normalisée **sans tirets** (32 caractères). Vérifié dans `inspect` **et** à nouveau dans la transaction de `claim`.
- Récompense : `booster` → `addBonusBoosters(setId, qty)`, `card` → `addCardToCollection(card, qty)`. Historique : même format qu'à l'Étape 9 (`category: "codes"`, `line: "code:<redeemId>:0"`), sans stocker le code.

### 4. `DeepLink.js` & intégration `app.js`
1. **Le plus tôt possible** au chargement (avant l'onboarding), lire `new URLSearchParams(location.search).get("Redeem")` (accepter aussi `redeem`). Si présent : le stocker dans `sessionStorage["pendingRedeem"]` puis **retirer le paramètre de l'URL** (`history.replaceState`) pour qu'un rechargement ne le rejoue pas. Ajouter `<meta name="referrer" content="no-referrer">` dans `index.html`.
   *(Exception assumée à la règle "pas de storage hors IndexedDB" de `main.md` : `sessionStorage` est transitoire et indispensable car l'import d'une sauvegarde recharge la page. La clé est supprimée dès le traitement.)*
2. **Pas de compte** : onboarding normal, avec un bandeau neutre "Un code est en attente, il sera vérifié après la création ou l'import de votre sauvegarde" (ne jamais afficher le code). Le traitement a lieu une fois le compte prêt et l'app démarrée. Cas d'usage : un code `useritem` ouvert sur un nouvel appareil, puis restauration du `.save` qui rétablit l'UUID d'origine.
3. **Compte présent, app démarrée et `DateSyncManager.init()` terminé** : lire puis supprimer `pendingRedeem`, appeler `RedeemManager.inspect(code)` :
   - `ok` → router vers la vue Redeem et ouvrir **directement** le modal de réclamation (même composant que `RedeemView`, aperçu des récompenses + "Récupérer" / "Annuler"). **Jamais de claim automatique** : un lien ne doit pas modifier la base sans clic.
   - `already_used`, `wrong_user`, `invalid_format`, `invalid`, `unknown`, `expired`, `not_yet_available`, `invalid_config` → **aucune popup** ; arrivée sur la vue par défaut + toast d'erreur traduit.
4. `claim` réussi → toast + header mis à jour via `QUOTA_UPDATED`, retour à la vue Redeem (ou Ouverture si booster offert, au choix de l'implémentation).

### 5. i18n
Nouvelles clés FR/EN : `redeem.error.wrong_user`, `redeem.error.invalid_format`, `redeem.pending_banner`, plus celles de l'Étape 9 si manquantes.

## Vérifications
- `selfTest()` passe avec les vecteurs du document.
- Code valide pour l'UUID A : `ok` sur A, `wrong_user` sur B (en général ; voir le document pour la limite de 16 bits), `already_used` après claim.
- Un caractère modifié → `invalid`. Saisie en minuscules, avec/sans tirets, `O`/`0` confondus : acceptée.
- `index.html?Redeem=<code ok>` : popup directe, URL nettoyée, rechargement sans repopup.
- `?Redeem=<code déjà utilisé>` et `?Redeem=<code d'un autre compte>` : pas de popup, toast.
- `?Redeem=<code>` sans compte : onboarding, puis traitement après création/import (le code personnel d'un UUID importé fonctionne).
- Fermer l'onglet entre le clic "Récupérer" et la fin : transaction atomique, pas d'état à moitié appliqué.

Génère le code complet.
